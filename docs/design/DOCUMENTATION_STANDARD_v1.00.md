# DOCUMENTATION STANDARD — Словасьянс

> **Статус:** зафиксированный стандарт
> **Версия:** 1.00
> **Область:** именование, версии и статусы проектных документов Словасьянса

## 1. Главный принцип

Имена и номера версий всех проектных документов должны быть однотипными и однозначными.

Нельзя использовать разные способы записи одной и той же стадии документа.

Плохо:

```text
v1.1
v0.11
```

если в обоих случаях подразумевается одиннадцатая рабочая редакция.

## 2. Формат имени файла

Используется формат:

```text
DOCUMENT_NAME_vMAJOR.MINOR.md
```

Где:

- `DOCUMENT_NAME` — стабильное имя документа в `UPPER_SNAKE_CASE`;
- `MAJOR` — статусная major-версия;
- `MINOR` — всегда две цифры.

Примеры:

```text
GAME_VISION_MANIFEST_v0.07.md
WORLD_FOREST_DOSSIER_v0.09.md
CHARACTER_WORLD_MANIFEST_v0.11.md
WORLD_CAMPAIGN_MANIFEST_v0.15.md
RARITY_SYSTEM_v1.00.md
```

## 3. Рабочие документы

Пока документ проектируется и не зафиксирован как стабильный, он остаётся в major `0`.

Рабочая последовательность:

```text
v0.01
v0.02
v0.03
...
v0.08
v0.09
v0.10
v0.11
v0.12
...
v0.99
```

Жёсткое правило:

> **После `v0.09` идёт `v0.10`, а не `v1.0`.**

Major-версия не повышается автоматически из-за перехода через девятую редакцию.

## 4. Стабильная версия

`v1.00` означает отдельное событие:

> **документ утверждён как первая стабильная версия.**

То есть `v1.00` — не «десятая рабочая редакция».

После утверждения допустимы:

```text
v1.01
v1.02
v1.03
```

для совместимых уточнений стабильного документа.

Существенный пересмотр базовой модели может привести к:

```text
v2.00
```

Но повышение major должно быть осознанным решением, а не арифметическим переносом разряда.

## 5. Две цифры после точки обязательны

Всегда:

```text
v0.07
v0.09
v0.11
v1.00
v1.01
```

Не использовать:

```text
v0.7
v0.9
v1.0
v1.1
```

Это устраняет визуальную двусмысленность и делает сортировку файлов предсказуемой.

## 6. Версия внутри документа

Номер версии внутри документа обязан точно совпадать с именем файла.

Например:

```text
WORLD_CAMPAIGN_MANIFEST_v0.15.md
```

внутри содержит:

```text
Статус: рабочий манифест v0.15
```

Недопустимо, чтобы имя файла и заголовок расходились.

## 7. Статус и версия — разные вещи

Версия не заменяет статус.

Допустимые статусы определяются назначением документа, например:

- черновой;
- рабочий;
- рабочий канон;
- зафиксированный;
- утверждённый;
- deprecated / архивный.

Например:

```text
Статус: черновой world dossier
Версия: 0.09
```

и:

```text
Статус: зафиксированный дизайн-спек
Версия: 1.00
```

— разные состояния документа, даже если оба используют общий формат версии.

## 8. Нельзя тихо перенумеровывать историю

Если документ уже использовался как конкретная версия, новая содержательная редакция получает следующий номер.

Допускается только одно техническое исключение:

> **нормализация старого ошибочного формата без изменения содержания.**

Например текущий:

```text
WORLD_CAMPAIGN_MANIFEST_v1.5.md
```

нормализуется в:

```text
WORLD_CAMPAIGN_MANIFEST_v0.15.md
```

потому что `v1.5` возникло как продолжение последовательности рабочих `v0.6 ... v0.9`, а не как осознанное утверждение stable major `1`.

## 9. Имена документов

Базовое имя документа не меняется между версиями.

Правильно:

```text
WORLD_FOREST_DOSSIER_v0.09.md
WORLD_FOREST_DOSSIER_v0.10.md
WORLD_FOREST_DOSSIER_v0.11.md
```

Неправильно:

```text
FOREST_WORLD_v0.09.md
WORLD_FOREST_NEW_v0.10.md
FOREST_DOSSIER_FINAL_v0.11.md
```

Слова `NEW`, `FINAL`, `FINAL2`, `LATEST`, `UPDATED` в именах версионных документов не используются.

## 10. Каноническая короткая формула

> **Стабильное имя. Две цифры версии. Рабочее остаётся `v0.XX`. `v1.00` только после осознанной фиксации.**
